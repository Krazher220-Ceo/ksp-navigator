# Как выложить кабинет на Vercel и что потом проверить

Документ отвечает ровно на два вопроса, которые задал автор:
**«какие ветки нужны и не надо ли делать это отдельно»** и **«как
проверить, что всё работает»**. Всё, что здесь написано, проверено по
самому репозиторию: адрес удалённого репозитория, набор веток,
переменные окружения — не по памяти.

---

## 0. Что вообще куда едет

У продукта две половины, и на Vercel уезжает **только одна**.

| Часть | Где живёт сейчас | Куда едет |
|---|---|---|
| Кабинет и сайт (`frontend/`, Next.js) | `npm run dev` на MacBook | **Vercel** |
| API, бот, очередь (`web/`, `bot/`, `core/`) | MacBook, launchd + Cloudflare Tunnel | **остаётся на MacBook** |
| База и вход по почте | Supabase (облако) | остаётся как есть |

Переносить FastAPI на Vercel нельзя и не нужно: там нет ни очереди с
повторами, ни `ffmpeg`, ни `soffice`, а функции живут секунды —
расшифровка урока в них не помещается. Переезд API на VPS — отдельное
решение автора (`FRONTEND_PLAN.md`, раздел 6).

**Отсюда главное следствие:** сайт на Vercel будет ходить по `https`, а
API обязан отвечать тоже по `https` — с того же адреса, что уже стоит в
`WEBAPP_URL` (туннель Cloudflare). Браузер не даст странице на `https`
дёрнуть `http://localhost:8000`, и это будет выглядеть как «сайт есть, а
кнопки не работают».

---

## 1. Ветки: отдельный репозиторий не нужен

Сейчас в репозитории две ветки:

```
main
claude/gracious-ritchie-171048
```

Vercel умеет работать с монорепозиторием — достаточно указать, что
проект лежит в подпапке. **Отдельный репозиторий для фронтенда заводить
не надо**, и выносить `frontend/` в свой репозиторий тоже не надо: тесты
кабинета (`tests/test_frontend_*.py`) лежат рядом с кодом и сверяются с
`design/`, а после разделения они перестанут это делать.

Схема веток такая:

- **`main`** → боевой адрес (`mazmun.vercel.app`, потом свой домен).
  Vercel сам пересобирает сайт на каждый `git push` в `main`.
- **любая другая ветка** → превью-адрес вида
  `mazmun-git-<ветка>.vercel.app`. Отдельно настраивать ничего не нужно:
  это поведение по умолчанию.

То есть **никакой третьей ветки заводить не надо**. Работа идёт в
`main`, превью появляются сами на всём остальном.

Одна оговорка: `claude/gracious-ritchie-171048` — рабочая ветка, и после
подключения к Vercel каждый её push тоже будет собирать превью. Это
безвредно (превью закрыты авторизацией Vercel), но если раздражает —
её можно просто удалить, когда она станет не нужна.

## 2. Порядок действий (по шагам)

### Шаг 1. Отправить код на GitHub

Push делает автор — ассистент этого не делает никогда.

```bash
git log --oneline -12
```

```bash
cd /Users/kr220/Documents/Projects/ksp-navigator && git push origin main
```

### Шаг 2. Создать проект на Vercel

1. `vercel.com` → **Add New… → Project** → **Import Git Repository** →
   `Krazher220-Ceo/ksp-navigator`.
2. В открывшейся форме нажать **Edit** рядом с **Root Directory** и
   выбрать **`frontend`**. Это единственная неочевидная настройка: без
   неё Vercel будет искать `package.json` в корне и упадёт.
3. Framework Preset определится сам — **Next.js**. Build Command,
   Output Directory, Install Command трогать не надо.
4. Node.js Version — 22.x (по умолчанию).
5. **Не нажимать Deploy сразу** — сначала шаг 3, иначе первая сборка
   упадёт на отсутствующих переменных.

Файл `vercel.json` в проекте не нужен и его нет: всё, что он мог бы
задать, задаётся в этой форме.

### Шаг 3. Переменные окружения на Vercel

В той же форме (или потом: **Settings → Environment Variables**)
завести пять переменных. Значения — из `frontend/.env.example`, где
описано, что каждая означает.

| Переменная | Значение | Окружения |
|---|---|---|
| `NEXT_PUBLIC_API_URL` | адрес туннеля, тот же, что в `WEBAPP_URL` в `.env`, **без завершающего слэша** | Production, Preview |
| `NEXT_PUBLIC_SUPABASE_URL` | `https://<проект>.supabase.co` | Production, Preview |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | ключ **anon**, он же publishable | Production, Preview |
| `NEXT_PUBLIC_TELEGRAM_BOT_URL` | `https://t.me/<имя_бота>` | Production, Preview |
| `NEXT_PUBLIC_TELEGRAM_BOT_NAME` | имя бота **без `@`** | Production, Preview |

⚠️ **`SUPABASE_SERVICE_ROLE_KEY` на Vercel не заводится никогда.** Он
даёт полный доступ к базе мимо всех проверок, а всё с приставкой
`NEXT_PUBLIC_` попадает в бандл, который скачивает браузер. Ключи бота,
`XAI_API_KEY`, `GROK_API_KEY` там тоже не нужны — они живут только в
`.env` на MacBook.

### Шаг 4. Первая сборка

**Deploy**. Сборка занимает около минуты. Локально она уже проходит
(`npm run build` — 17 страниц, ошибок нет), так что падение здесь почти
наверняка означает забытую переменную из шага 3.

### Шаг 5. Пустить браузер обратно к API (без этого ничего не заработает)

Пока не сделано — кабинет откроется, но каждая кнопка будет отвечать
«сервер недоступен». Причина: CORS. Сервер отдаёт данные только тем
адресам, которые перечислены явно; звёздочки там нет намеренно.

В `.env` на MacBook:

```
CORS_ORIGINS=http://localhost:3000,https://<адрес>.vercel.app
```

Через запятую, без пробелов, с протоколом — и **без завершающего
слэша**. Браузер присылает в `Origin` голый адрес, поэтому запись
`https://x.vercel.app/` не совпадает ни с чем; сайт при этом
открывается, а каждая кнопка отвечает «сервер недоступен». Ровно на
это ушёл день 02.09.2026. Второй раз так не выйдет — разбор теперь
слэш срезает, — но писать сразу правильно дешевле.

Адрес нужен **боевой** (`ksp-navigator.vercel.app`), а не адрес ветки:
человек заходит на боевой. Служебные адреса Vercel можно дописать
рядом, лишними они не будут.

Затем перезапустить API:

```bash
launchctl kickstart -k gui/$(id -u)/com.alikhan.webapi
```

Когда появится свой домен — дописать и его, старый адрес не убирая:
превью-сборки продолжат работать.

### Шаг 6. Разрешить Supabase возвращать людей на новый адрес

Supabase → **Authentication → URL Configuration**:

- **Site URL** — боевой адрес Vercel;
- **Redirect URLs** — туда же добавить `https://<адрес>.vercel.app/**`.

Без этого письмо «подтвердите почту» и ссылка на смену пароля вернут
человека на `localhost:3000`, то есть в никуда.

### Шаг 7. Разрешить виджету Telegram работать на этом домене

В `@BotFather`: `/setdomain` → выбрать бота → вписать домен кабинета
(`mazmun.vercel.app`, без `https://` и без пути).

Пока это не сделано, кнопка «Войти через Telegram» на `/vhod` просто не
нарисуется — виджет Telegram молча отказывается работать на чужом
домене. Именно поэтому под ним стоит подпись «Загружаю кнопку
Telegram…»: пустое место без объяснения — худший вариант.

Домен задаётся **один**. Пока идёт проверка на превью-адресах, вход
через Telegram будет работать только на том адресе, который вписан.

### Шаг 8. Свой домен (когда автор его купит)

Покупка домена — решение автора (`FRONTEND_PLAN.md`, раздел 6).
После покупки: Vercel → **Settings → Domains** → добавить домен,
прописать у регистратора выданные записи. Затем повторить шаги 5, 6, 7
уже для нового адреса — все три места помнят адрес отдельно.

## 3. Что проверить после выкладки

Список составлен так, чтобы каждый пункт **падал по-разному**: если
что-то не работает, по номеру пункта видно, где именно.

### Сначала — на MacBook, до всякого Vercel

| # | Что сделать | Что должно быть |
|---|---|---|
| 1 | `./venv/bin/python -m pytest -q` | `1100 passed`, один известный `failed` в `test_bot_handlers.py` — чужая задача |
| 2 | `cd frontend && npm run check` | «токены сверены… 31 шт.», «иконки сверены… 50 шт.» |
| 3 | `cd frontend && npm run build` | `✓ Compiled successfully`, 17 страниц |
| 4 | `curl -s -o /dev/null -w '%{http_code}\n' $WEBAPP_URL/api/v1/health` | `200` |

### Потом — в браузере на боевом адресе

| # | Экран | Что нажать | Что должно произойти |
|---|---|---|---|
| 5 | `/` | пролистать до низа | блоки появляются по мере прокрутки; **синяя точка между карточками «Запись → Расшифровка → Конспект» не вылетает за пунктирную линию** — это то, что было на скриншоте |
| 6 | `/docs` | нажать пункты в правом оглавлении | страница едет плавно, а не прыгает; читаемый раздел подсвечен синим с полоской слева |
| 7 | `/registraciya` | пройти регистрацию до конца | либо кабинет, либо экран «Подтвердите почту» с понятным текстом — но **не** пустая страница и не «ничего не произошло» |
| 8 | почта | открыть письмо Supabase | ссылка ведёт на боевой адрес, а не на `localhost` (шаг 6) |
| 9 | `/vhod` | нажать «Войти через Telegram» | всплывает окно Telegram, после подтверждения — кабинет с вашим именем в левом нижнем углу (шаг 7) |
| 10 | `/vhod` | войти почтой и паролем | кабинет; при неверном пароле — «Не удалось войти: проверьте почту и пароль» |
| 11 | `/app` | открыть на телефоне | **снизу пять вкладок**, бокового меню нет, последняя карточка не спрятана под панелью |
| 12 | телефон, вкладка «Ещё» | нажать | снизу выезжает лист со всеми разделами; нажатие на раздел его закрывает |

| 14 | `/app/ustanovka` на телефоне | по инструкции | «На экран Домой» ставит иконку; приложение открывается без адресной строки |
| 15 | установленное приложение | включить авиарежим и открыть | открывается, а не «нет соединения» — это и есть PWA |

### Как поставить приложение на телефон (PWA)

Включать нечего — PWA уже собран и на боевом адресе живой: манифест,
service worker и обе иконки отдаются с кодом 200. Кнопки «установить» на
сайте нет и на iPhone быть не может: там установку делает только сам
браузер.

**iPhone и iPad.** Открыть `ksp-navigator.vercel.app` **в Safari** —
именно в Safari, из Chrome на iOS установка недоступна. Кнопка
«Поделиться» (квадрат со стрелкой вверх) → пролистать список вниз → **«На
экран „Домой“»** → «Добавить». На домашнем экране появится иконка
Mazmun, приложение откроется без адресной строки.

**Android.** Открыть в Chrome → меню (три точки) → **«Установить
приложение»** или «Добавить на главный экран». На части телефонов Chrome
сам показывает полоску с предложением установить.

**Компьютер.** Chrome или Edge → значок установки в правом краю адресной
строки.

Если пункта «На экран „Домой“» нет — почти всегда одно из трёх: открыто
не в Safari, открыто в приватном окне, или адрес не `https`.

### Про пункт 15 — почему «ПВА не было» в разработке

Service worker намеренно не регистрируется в режиме разработки
(`components/pwa/РегистрацияSW.tsx`): закэшированный дев-бандл — верный
способ полдня чинить уже исправленное. Поэтому в `npm run dev` PWA не
появляется никогда, сколько ни обновляй страницу, — и выглядит это как
«ПВА нет». На Vercel сборка боевая и по `https`, так что установка
заработает сама, без единой правки кода.

### Если что-то не работает

| Симптом | Где смотреть |
|---|---|
| Сайт открылся, любая кнопка → «сервер недоступен» | шаг 5, `CORS_ORIGINS`. В консоли браузера будет строка про CORS |
| Кнопки Telegram на `/vhod` нет вовсе | шаг 7, `/setdomain`, либо не задан `NEXT_PUBLIC_TELEGRAM_BOT_NAME` |
| Письмо возвращает на `localhost` | шаг 6, Redirect URLs |
| Сборка падает на Vercel | Root Directory ≠ `frontend` (шаг 2) или забытая переменная (шаг 3) |
| Кабинет пустой, сразу выкидывает на `/vhod` | API не отвечает: `launchctl print gui/$(id -u)/com.alikhan.webapi` |
| Ссылка из письма приводит на лендинг | Redirect URLs в Supabase (шаг 6): без боевого адреса в списке Supabase игнорирует `emailRedirectTo` и подставляет Site URL |
| Страница с английским «404 — This page could not be found» | адрес, которого нет. Своя русская страница 404 показывается на всех остальных промахах |

Быстрая проверка CORS, не открывая браузер — подставьте свой адрес:

```bash
curl -s -X OPTIONS https://ksp.alikhandev.com/api/v1/me -H 'Origin: https://ksp-navigator.vercel.app' -H 'Access-Control-Request-Method: GET' -i | head -3
```

`200` и строка `access-control-allow-origin` — всё в порядке.
`400 Disallowed CORS origin` — адрес не в списке.

## 4. Чего этот документ не решает

Всё это — решения автора, а не работа ассистента
(`FRONTEND_PLAN.md`, раздел 6):

- покупка домена;
- переезд API с MacBook на VPS;
- включение оплаты (в коде лежат только выключенные заглушки тарифов);
- казахская версия интерфейса;
- любая новая таблица или колонка в Supabase.
