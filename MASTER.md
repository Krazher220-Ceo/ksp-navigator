# ЧАСТЬ 0. ПРАВИЛА РАБОТЫ (обязательны к исполнению любой моделью)

Этот раздел читается первым и имеет приоритет над всем остальным содержимым документа.

## 0.1. Git — локальные коммиты можно, удалённая история — нет

> **Пересмотрено 25.08.2026 решением автора.** Исходная редакция запрещала ассистенту любые git-команды. Практика показала, что при длинных автономных сессиях (несколько блоков подряд, ночью, без человека за клавиатурой) это приводит к потере работы между блоками и к огромным неразделённым диффам, которые невозможно ревьюить. Правило смягчено ровно настолько, насколько нужно, чтобы работа сохранялась поблочно.

Ассистент (Claude Code, любая модель — Opus, Sonnet, Haiku) **может**:
- `git add <явно перечисленные файлы>`, `git commit`
- `git status`, `git diff`, `git log`, `git show` — чтение состояния

Ассистенту **запрещено всегда**:
- `git push`, `git pull`, `git merge`, `git rebase`, `git reset --hard`, `git tag`, `git init`
- `gh pr create`, `gh pr merge`, `gh release create` и любые команды `gh`, меняющие состояние
- любые операции, переписывающие уже существующую историю или трогающие удалённый репозиторий

Push автор делает сам, из терминала, посмотрев `git log` и `git diff`.

**Причина, по которой удалённое остаётся за автором:** у проекта один автор, и история удалённого репозитория — доказательство авторства проекта. Локальный коммит автор всегда может переписать или отменить до push; отправленный — уже нет.

## 0.2. Никаких следов ассистента в истории

Это правило **не** смягчалось и не смягчается.

В сообщениях коммитов, в описаниях PR, в тегах и в CHANGELOG **запрещены**:
- строки вида `Co-Authored-By: Claude <...>` и любые другие `Co-Authored-By`
- `Generated with Claude Code`, `🤖 Generated with ...`
- упоминания моделей (Claude, Opus, Sonnet, Haiku, GPT) и ссылки на claude.com / anthropic.com

Сообщение коммита пишется так, как написал бы его автор: по-русски, по существу, в формате `stage1: краткое описание блока`. Ассистент — инструмент автора, а не соавтор.

**Гигиена перед каждым коммитом:**
- `git status` — убедиться, что не утягиваются `.env`, `storage/app.db`, `backup/`, мусорная папка `https:/` в корне и любые чужие файлы
- не использовать `git add .` — перечислять файлы явно
- один блок работ = один коммит; не сваливать три блока в один

Проверить один раз перед первым коммитом:

```bash
git config user.name && git config user.email
```

Должны стоять данные автора, а не что-либо другое.

## 0.3. Формат сдачи работы ассистентом

После каждого блока работ ассистент обязан выдать ровно три вещи:

1. **Список изменённых/созданных файлов** — путь + одна строка, что там.
2. **Что проверить руками** — конкретные команды запуска и ожидаемый результат.
3. **Коммит блока** — по правилу 0.1 ассистент делает его сам, перечисляя файлы явно:

```bash
git add core/foo.py tests/test_foo.py && git commit -m "stage1: краткое описание блока"
```

Push не делает — это автор, из терминала.

**Режим работы определяет, останавливаться ли после блока:**
- *Интерактивный* (автор за клавиатурой) — остановиться после блока и ждать.
- *Автономный* (запуск на ночь по `PROMPTS_STAGE2.md`) — закоммитить блок и идти к следующему, не спрашивая. Останавливаться только на том, что явно помечено в плане как требующее решения автора.

**2. Цепочка конспекта — только через аудио.** Конспект урока делается из
аудиозаписи, и уже по конспекту собирается КСП:

```
аудиозапись урока → xAI STT → транскрипт → конспект → КСП
```

Генерации конспекта «из темы и учебника, без записи» в проекте нет и не
планируется — конспект по определению фиксирует то, что реально прозвучало

«ровно два экрана» из раздела 7.1 и пункт «не делать третий экран» из
раздела 11. Причина: данные для дашборда в базе уже есть, а без него автор не
видит состояния собственной системы. Ограничение «Mini App ничего не
редактирует» **остаётся в силе** — третий экран только показывает.

**4. Supabase и pgvector откладываются до этапа 6.** Это отменяет фразу из
раздела 3.2 «на этом этапе SQLite уже не хватает — переход на Supabase +
pgvector». На реальном масштабе этапа 3 (один учитель, один предмет, десятки
уроков) векторов сотни, а не десятки тысяч: полный перебор в Python быстрее
сетевого round-trip до Supabase, а pgvector нужен там, где требуется индексный
поиск. Векторы хранятся `BLOB`-ами в той же SQLite. Пересмотреть при переходе
к нескольким учителям.

**5. Вводятся дневные лимиты на аккаунт.** Не ради экономии денег (расход
копеечный), а чтобы одна ошибка в коде или один заскучавший пользователь не
съели дневной лимит провайдера и не оставили систему без генерации до утра:

| Что | Лимит в сутки на аккаунт |
|---|---|
| Генерация КСП | 5 |
| Генерация КТП | 2 |
| Остальные операции (конспект, транскрипция, распознавание фото) | по количеству не ограничены |
| **Общий потолок токенов LLM** | **1 000 000 в сутки** |

Общий потолок — жёсткий: он останавливает всё, включая безлимитные по
количеству операции. Транскрипция тарифицируется аудиоминутами, а не токенами
LLM, поэтому под этот потолок не попадает.

**6. Дорожная карта после этапа 2** (уточняет ЭТАП 5 ниже). Порядок такой:
сначала PWA-веб-приложение, затем Android, затем iOS. Android раньше iOS
намеренно — публикация проще и дешевле. Telegram-бот при этом не
выбрасывается: он остаётся самым быстрым способом закинуть файл с телефона.

# ЧАСТЬ I. АНАЛИЗ И ПОЗИЦИОНИРОВАНИЕ

## 1. Что это за проект на самом деле

Проект прошёл три итерации формулировки, и финальная версия такая:

**Система, которая связывает четыре независимых слоя данных об учебном процессе и показывает расхождения между ними.**

| Слой | Что это | Откуда берётся |
|---|---|---|
| **Норма** | Что *должно* быть пройдено | Типовая учебная программа МОН РК, коды целей (10.1.1.1) |
| **План** | Что учитель *запланировал* | КТП (календарно-тематический план) + КСП (поурочный план) |
| **Факт** | Что *реально* произошло на уроке | Аудиозапись → транскрипт |
| **Усвоение** | Что ученик *унёс* с урока | Фото конспекта → OCR |

Ценность не в транскрипции. Транскрипция — способ получить слой «Факт». Ценность — в **разнице между слоями**:
- Норма ↔ Факт = покрытие программы (полезно учителю)
- План ↔ Факт = отклонение от КСП (полезно учителю)
- Факт ↔ Усвоение = что ученик пропустил (полезно ученику)

## 2. Честная оценка: где проект силён и где слаб

**Сильные стороны (реальные, не самообман):**
- Ниша действительно свободна. Ни Otter, ни Notta, ни NotebookLM не знают про коды целей РК и форму КСП по приказу №130.
- Боль подтверждена рынком: готовые КСП продаются на plani.kz за ~3600 тг за комплект. Люди платят деньги за то, что ты хочешь автоматизировать.
- Форма КСП утверждена законом и **неизменна** — это идеальный шаблон для генерации, потому что структура фиксирована и не надо угадывать формат.
- У тебя есть доступ к реальным данным (свои уроки, свои учителя) — то, чего нет у стороннего разработчика.

**Слабые стороны (то, что убьёт проект, если игнорировать):**
- **Час в неделю.** Это главное ограничение, не деньги и не технологии. Любая фича сверх минимума = месяцы задержки.
- **Три пользователя в одном продукте** (ты как ученик, учитель через КСП, учитель через аналитику) — при твоём ресурсе это три разных продукта. Нужно выбрать один и довести.
- **OCR рукописного кириллического текста** — точность 30–70%. Слой «Усвоение» технически самый сложный, а выглядит самым простым. Не начинай с него.
- **STT на смеси русского и казахского** — качество нужно проверять на
  реальных записях. Физика на одном языке — первый поддержанный сценарий.
- **Ноль накопленных данных.** Прошлые формативки удалены, учителя сменились. Любая фича предсказания невозможна раньше января.

## 3. Стратегическое решение: с чего начинать

**Начинаем с КСП-генератора для учителя. Не с транскрипции.**

Почему:
1. Не требует записи урока → не требует согласия → нет юридических вопросов на старте
2. Даёт учителю пользу в первый же день → он становится союзником, а не объектом
3. Форма закреплена законом → результат проверяемый, не размытый
4. Не требует накопления данных → работает с 2–3 прошлыми КСП сразу
5. Технически проще всего → реально уложиться в час в неделю

Транскрипция подключается вторым этапом, когда уже есть доверие учителя и работающий продукт в руках.

## 4. Приказ №130 — форма КСП (главный документ)

**Приказ Министра образования и науки РК от 6 апреля 2020 года № 130** «Об утверждении Перечня документов, обязательных для ведения педагогами...», зарегистрирован в Минюсте под № 20317.

🔗 https://adilet.zan.kz/rus/docs/V2000020317

Что важно из него:
- Педагог **на каждый урок** разрабатывает краткосрочный (поурочный) план — в бумажном или электронном формате Word или PDF
- **Один раз до начала учебного года** разрабатывает среднесрочный (календарно-тематический) план по предметам
- По итогам четверти — анализ СОР и СОЧ, формируется автоматически из АИС

> (календарно-тематический) план по предметам …»

расписанию». Правильная опора — процитировать приложение 3, пункт 1.

> «Данные пункты плана урока являются обязательными.»

> государственного общеобязательного стандарта …»

## 7. Язык и стек — обоснование

Ты спросил, нужен ли Python. Ответ: **да, но не для всего.**

### Python — для пайплайна обработки
Не потому что «так принято», а по конкретным причинам:
- xAI STT вызывается через HTTP — Python здесь просто клей
- Обработка docx (`python-docx`), PDF, OCR (`pytesseract`) — экосистема готовых библиотек, которых нет в других языках
- LLM SDK, работа с эмбеддингами — Python-first экосистема
- Если писать это на Go/Rust — придётся руками реализовывать то, что в Python есть готовым. При часе в неделю это самоубийство.

### TypeScript — для интерфейса (позже)
- Next.js/React для веб-версии
- Общий язык фронта и API-роутов
- Vercel деплоится бесплатно

### Что НЕ выбирать и почему
| Вариант | Почему нет |
|---|---|
| Всё на Rust/Go | Скорость не узкое место (узкое — сетевые API и LLM). Потеряешь недели на реализацию того, что в Python готово |
| Всё на JS/TS включая пайплайн | Обработка docx/OCR/аудио в Node — боль, библиотеки хуже |
| Java/C# | Избыточно для проекта такого размера |

## 7.1 Telegram Mini App — зачем и в каком объёме

Чат-бот плохо показывает таблицы, шаблоны и предпросмотр КСП. Mini App решает это, оставаясь внутри Telegram — не нужен отдельный логин, ссылка открывается кнопкой в чате.

**Но честное предупреждение:** Mini App — это полноценный веб-фронтенд, просто открытый внутри Telegram. Он требует HTTPS-хостинга, валидации `initData` на бэкенде и своей вёрстки. Это НЕ «бот, но красивее». При часе в неделю легко утонуть.

**Поэтому правило: Mini App на этапе 1 — ровно два экрана и ничего больше.**

| Экран | Что делает | Чего НЕ делает |
|---|---|---|
| **Шаблоны** | Список доступных шаблонов КСП, выбор одного, кнопка «загрузить свой» | Не редактирует шаблоны, не создаёт новые |
| **Предпросмотр** | Показывает сгенерированный КСП таблицей, кнопка «скачать .docx» | Не редактирует текст, не сохраняет правки |

Всё остальное — команды, загрузка файлов, статусы — остаётся в боте. Mini App только там, где чат физически не справляется.

**Технически на этапе 1:**
- Обычный `index.html` + чистый JS, без React и сборки
- Раздаётся с того же Mac через Cloudflare Tunnel (бесплатный HTTPS-домен без белого IP — Telegram требует HTTPS)
- Telegram Web App SDK: `telegram-web-app.js`, тема берётся из `themeParams` — тёмная автоматически
- Обязательно: валидация `initData` через HMAC на бэкенде, иначе любой сможет дёргать твой API

## 7.2 Граница Claude Code — до какого момента

Ты прав, что Claude Code хорошо тянет до MVP и хуже — дальше. Причина конкретная: он отлично пишет код по чёткому ТЗ в понятной структуре, но плохо держит в голове разрастающуюся кодовую базу с накопленными архитектурными компромиссами.

| Фаза | Кто пишет | Почему |
|---|---|---|
| **Этапы 1–3** | Claude Code | Задачи изолированные, ТЗ есть, код в основном скриптовый — идеальные условия |
| **Этап 5** (полноценный веб) | Claude Code для черновика, дальше — живой фронтендер или ты сам | UI-состояния, роутинг, доступность, отзывчивость — здесь нужен человек с вкусом и насмотренностью |
| **Этапы 6–7** (мультипользовательность) | Человек | Аутентификация, разделение доступа, миграции данных — цена ошибки высокая, а ошибка неочевидная |

**Практический вывод:** пиши код так, чтобы его потом можно было отдать человеку. Это значит — понятные имена, README, никакой магии, все решения задокументированы в этом файле. Не «как быстрее», а «как понятнее для того, кто придёт после».

### 1.1.1 Библиотека шаблонов — уточнение

Загруженные КТП/КСП из интернета — это **не** данные конкретного учителя, а **образцы оформления**. Их нельзя мешать в одну кучу с реальными КСП физика: разные учебники, разное количество работ, разная структура.

Поэтому в базе — два независимых понятия:

| | Шаблон (template) | Профиль стиля (style_profile) |
|---|---|---|
| Что это | Образец структуры и оформления | Манера конкретного учителя |
| Откуда | Встроенная библиотека или загрузка пользователем | Из 2–5 реальных КСП этого учителя |
| Сколько | Много, на выбор | Один на учителя |
| Влияет на | Форму, порядок блоков, оформление | Формулировки, методы, тайминг |

При генерации пользователь выбирает шаблон **и** (опционально) профиль стиля. Есть профиль — КСП будет в манере учителя; нет профиля — просто корректный КСП по выбранному шаблону.

**Стартовая библиотека (уже есть):**
1. Официальная форма по приказу №130 — минимальная, юридически обязательная. **Дефолт.**
2. Развёрнутый образец с колонками «домашнее задание / ресурсы / доп. литература» — из найденного КТП (13 лаб., 17 практ., 5 контр.)
3. Образец КГУ «Гимназия №27» — с колонками «раздел / тема / цели обучения / часы / дата»

Обязательное поле у каждого шаблона — `source` (откуда взят) и `is_official` (соответствует ли приказу №130). Пользователь должен видеть, что официально, а что нет.

### 1.3 Схема базы данных (этап 1)

```sql
CREATE TABLE teachers (
    id INTEGER PRIMARY KEY,
    name TEXT,
    subject TEXT,
    telegram_user_id INTEGER,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE style_profiles (
    id INTEGER PRIMARY KEY,
    teacher_id INTEGER REFERENCES teachers(id),
    -- извлечённые паттерны в JSON
    goal_phrasing TEXT,        -- как формулирует цели урока
    stage_structure TEXT,      -- типичные этапы и их тайминг
    assessment_methods TEXT,   -- любимые методы оценивания
    resources_used TEXT,       -- какие ресурсы обычно указывает
    raw_samples_count INTEGER,
    updated_at TIMESTAMP
);

CREATE TABLE templates (
    id INTEGER PRIMARY KEY,
    name TEXT NOT NULL,
    description TEXT,
    source TEXT,               -- откуда взят: приказ №130 / интернет / загружен
    is_official INTEGER DEFAULT 0,   -- соответствует приказу №130
    is_builtin INTEGER DEFAULT 0,    -- встроенный или загружен пользователем
    uploaded_by INTEGER REFERENCES teachers(id),  -- NULL для встроенных
    structure_json TEXT NOT NULL,    -- описание блоков и колонок
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE curriculum_objectives (
    code TEXT PRIMARY KEY,     -- 10.1.1.1
    grade INTEGER,
    section TEXT,
    subsection TEXT,
    description TEXT,
    thinking_level TEXT        -- знание/применение/высокий порядок
);

CREATE TABLE ktp_entries (
    id INTEGER PRIMARY KEY,
    teacher_id INTEGER REFERENCES teachers(id),
    lesson_number INTEGER,
    section TEXT,
    topic TEXT,
    objective_code TEXT REFERENCES curriculum_objectives(code),
    hours INTEGER,
    planned_date TEXT,
    quarter INTEGER
);

CREATE TABLE generated_ksp (
    id TEXT PRIMARY KEY,
    teacher_id INTEGER REFERENCES teachers(id),
    ktp_entry_id INTEGER REFERENCES ktp_entries(id),
    template_id INTEGER REFERENCES templates(id),
    content_json TEXT,
    docx_path TEXT,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE tasks (
    id TEXT PRIMARY KEY,
    type TEXT CHECK(type IN ('parse_ksp','generate_ksp')),
    status TEXT CHECK(status IN ('pending','processing','done','failed')) DEFAULT 'pending',
    payload TEXT,
    result TEXT,
    error TEXT,
    telegram_chat_id INTEGER,
    retries INTEGER DEFAULT 0,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP
);
```

## ЭТАП 3 — Coverage-аналитика ⭐ РАСПИСАН ПОДРОБНО

**Цель:** сопоставить три слоя (Норма / План / Факт) и показать расхождения. Это ядро ценности проекта.

### 3.1 Что именно считаем

**Аналитика А: Норма ↔ Факт (для учителя)**

Берём коды целей из КТП, привязанные к конкретному уроку. Берём транскрипт этого урока. Определяем, какие цели реально были затронуты.

Каждая цель обучения раскладывается на **элементы**:
```
Цель 10.1.4.1 «Применять законы сохранения при решении задач»
├── понятие введено           → найдено / не найдено
├── формула дана              → найдено / не найдено
├── вывод/обоснование         → найдено / не найдено
├── пример разобран           → найдено / не найдено
└── задача решена             → найдено / не найдено

Покрытие: 3/5 = 60%
```

**Аналитика Б: План ↔ Факт (для учителя)**

Сравниваем сгенерированный/загруженный КСП с транскриптом: какие этапы урока реально состоялись, сколько времени заняли по факту против плана.

```
Этап «Изучение нового материала»
  План: 20 мин
  Факт: 31 мин  (+11)

Этап «Закрепление»
  План: 10 мин
  Факт: 4 мин   (−6)

Этап «Рефлексия»
  План: 5 мин
  Факт: не обнаружен
```

**Аналитика В: Факт ↔ Усвоение (для ученика)**

Транскрипт против фото конспекта. Что учитель говорил, но в тетради нет.

```
На уроке найдено 19 значимых смысловых блоков
В конспекте обнаружено 14

Пропущено:
• условие применимости закона сохранения
• второй пример с шарами
• типичная ошибка при знаках импульса
```

### 3.2 Технический подход

**Не ключевые слова, а эмбеддинги.** Поиск по совпадению слов не сработает: учитель говорит «эта величина не меняется в замкнутой системе», а в программе написано «закон сохранения импульса». Нужна семантическая близость.

```
Пайплайн сопоставления:

1. Транскрипт → чанки по 3–5 предложений (с перекрытием)
2. Каждый чанк → эмбеддинг
3. Каждый элемент цели обучения → эмбеддинг
4. Косинусная близость каждый-к-каждому
5. Порог: > 0.75 = «затронуто», 0.60–0.75 = «частично», < 0.60 = «не найдено»
6. LLM-верификация пограничных случаев (0.60–0.80) — уточняющий запрос
```

Хранилище: на этом этапе SQLite уже не хватает — переход на **Supabase + pgvector**.

### 3.3 Принцип честности (критично)

Система **не имеет права** утверждать, что учитель чего-то не сделал. Она может утверждать только то, что не нашла в записи.

| ❌ Нельзя писать | ✅ Правильно писать |
|---|---|
| «Учитель не объяснил решение задач» | «В записи не обнаружено явного разбора решения задач» |
| «Тема не пройдена» | «Элементы цели 10.1.4.1 обнаружены частично (3 из 5)» |
| «Покрытие 60%» без пояснений | «Покрытие 60%, уверенность оценки 71%» |

Каждый вывод сопровождается **уровнем уверенности**. Это не формальность — это то, что делает возможным показывать отчёт учителю без конфликта.

### 3.5 KPI этапа 3

| KPI | Формула | Целевое |
|---|---|---|
| **Topic Precision** | TP / (TP + FP) | > 75% |
| **Topic Recall** | TP / (TP + FN) | > 70% |
| **Curriculum matching accuracy** | верно сопоставленных кодов / всего затронутых | > 80% |
| **Note coverage accuracy** | верно найденных пропусков / реальных пропусков | > 70% |
| **False positive rate** | приписанных уроку лишних тем / всего | < 15% |
| **Время анализа урока** | от загрузки до отчёта | < 5 мин |
| **Полезность (главный)** | пользователь называет ≥1 вещь, которую сам не заметил | да/нет |

**Замечание по Recall:** для этой задачи пропустить реальную тему хуже, чем добавить лишнюю. Порог лучше опустить и получить больше ложных срабатываний, чем потерять то, что было на уроке.

### 3.6 Экспериментальный протокол этапа 3

| Стадия | Объём | Что проверяем |
|---|---|---|
| Пилот | 1 урок | Цепочка работает без падений, отчёт формируется |
| Малая серия | 5 уроков | Стабильность, Precision/Recall на ручной разметке |
| Основная | 10–20 уроков | Появление трендов: темп программы, систематические пропуски |

Ручная разметка обязательна: ты сам слушаешь урок и отмечаешь, какие цели были затронуты. Это эталон, против которого меряется система. Без эталона все KPI выше — фикция.

## ЭТАП 4 — Предсказание тем СОР/СОЧ

**Гейт входа:** накоплено ≥ 6 формативок/СОР одного учителя + coverage-история за четверть.

**Что делаем:**
- Парсинг официальных спецификаций СОЧ (темы, уровни мышления, типы заданий, баллы)
- Ранжирование вероятных тем: вес в спецификации × время на уроке × повторяемость в прошлых работах
- Выдача с обоснованием и рейтингом важности 1–5, **никогда как гарантия**

**KPI:** доля реально попавшихся тем из предсказанных как высокоприоритетные.

⚠️ **Терминология:** СОР и СОЧ — оба **суммативные**. Формативное оценивание (ФО) — отдельная вещь. Называй фичу правильно, иначе учитель сразу увидит, что ты не разобрался.

# ЧАСТЬ VI. РИСКИ И РАЗГОВОР С УЧИТЕЛЕМ

## 10. Реестр рисков

| Риск | Вероятность | Влияние | Что делать |
|---|---|---|---|
| Час в неделю → сроки растягиваются | Высокая | Критическое | Жёстко резать фичи. Один этап за раз |
