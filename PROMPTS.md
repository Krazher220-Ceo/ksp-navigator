# PROMPTS.md — промпты для исполнителей

Готовые тексты, которые вставляются в Codex или Gemini. Копировать целиком,
включая последний абзац.

Три промпта:
- **Р** — работа по плану (основной);
- **А** — аудит без правок;
- **И** — исправление найденного аудитом.

---

## Промпт Р — работа по плану

```
Проект «Учебный навигатор»: Telegram-бот, который помогает педагогу
Республики Казахстан готовить КСП (краткосрочные поурочные планы по форме
приказа МОН РК №130), КТП и конспекты уроков из аудиозаписи. Работает на
MacBook автора через launchd, пользователей двое-трое. Python 3.11, aiogram 3,
SQLite, FastAPI для Mini App. Виртуальное окружение — venv в корне проекта.

ЧТО ПРОЧИТАТЬ ПЕРЕД РАБОТОЙ — РОВНО ДВА ФАЙЛА:
  MASTER.md — что за продукт и почему он такой
  PLAN.md   — план работ, по нему идёт вся работа

Больше ничего читать не нужно. PLAN.md написан самодостаточным: в разделе 2
пересказаны все грабли, на которые проект уже наступал. Папку archive/ не
открывать — там планы прошлых этапов, они описывают уже сделанное и только
собьют. Комментарии в коде ссылаются на старые номера блоков (Б6.2, Р1.1,
М4.2, К2.4) — это исторические пометки, искать их не надо.

ЧТО ДЕЛАТЬ

Идти по PLAN.md блоками, СТРОГО В ПОРЯДКЕ, ЗАДАННОМ В РАЗДЕЛЕ 3 плана.
Один блок за раз. Не забегать вперёд, не рефакторить соседние блоки «заодно».
Заметил проблему в другом блоке — записать в отчёт, не чинить сразу.

Порядок работы над каждым блоком:

  1. Прочитать блок целиком, включая все ловушки. Ловушки там не для красоты:
     каждая описывает ошибку, которую в этом проекте уже совершали.
  2. Написать код.
  3. Написать тест на то, что сделал. Если чинишь баг — тест ОБЯЗАН падать
     до правки. Проверить это НЕ рассуждением, а делом: временно откатить
     правку, прогнать тест, убедиться что упал, вернуть правку. В отчёте
     написать, сколько тестов реально упало на откате.
  4. Прогнать ВЕСЬ набор тестов, а не только новый:
       source venv/bin/activate && pytest -q
     Сейчас должно быть 531 passed. Меньше — значит что-то сломал.
  5. Закоммитить. Файлы перечислять явно, git add . запрещён.
  6. Если блок менял поведение бота — перезапустить его и проверить в Telegram:
       launchctl kickstart -k gui/$(id -u)/com.alikhan.kspbot
     Это обязательно. 27.08 полтора часа бот работал на старом коде, и целая
     группа функций в проде не работала ни разу, потому что его не перезапустили.
  7. Дописать в NIGHT_REPORT.md: что сделано, на какие грабли наступил, что
     автору проверить руками, хеш коммита.

ПРАВИЛА, НАРУШЕНИЕ КОТОРЫХ = ПЕРЕДЕЛКА

Git: можно git add, git commit, git status, git diff, git log, git show.
НЕЛЬЗЯ НИКОГДА: git push, git pull, git merge, git rebase, git reset --hard,
git tag, git init и любые gh, меняющие состояние. Push делает автор сам.

Ноль следов ассистента в коммитах. Запрещены Co-Authored-By в любом виде,
«Generated with», упоминания любых моделей и ассистентов (Claude, Gemini,
Codex, GPT, Copilot — любых), ссылки на сайты вендоров. Сообщение коммита
пишется так, как написал бы автор: по-русски, по существу, в формате
«stage-ux: краткое описание». Текст коммита для каждого блока уже указан в
самом блоке плана — брать его оттуда.

Ни одной новой зависимости — ни Python, ни JavaScript. Mini App остаётся
vanilla JS без сборки. Не получается без новой библиотеки — ОСТАНОВИТЬСЯ и
написать вопрос в отчёт, а не поставить молча.

Всё по-русски: комментарии, docstring, тексты бота, сообщения об ошибках.

Секреты только в .env (он в .gitignore). Не выводить содержимое .env ни в
чат, ни в лог, ни в отчёт. Пароли и ключи не придумывать в коде и не
коммитить — они читаются из .env, а в .env.example попадают пустыми.

Честность важнее зелёного прогона:
  - не писать «готово», не проверив;
  - не глушить ошибку try/except, чтобы тест прошёл. Не понял причину —
    так и написать в отчёт, это честнее;
  - не выдумывать содержимое файлов — открыть и прочитать;
  - тест, который проверяет «функция была вызвана» вместо реального
    результата, — это не тест.

КОГДА ОСТАНОВИТЬСЯ И СПРОСИТЬ АВТОРА

Список в разделе 6 плана. Коротко: любая новая зависимость; локальная LLM;
рост цены генерации заметно выше ориентира в блоке; необходимость форкнуть
build_prompt; системные настройки Mac, требующие пароля администратора.
Во всех этих случаях — записать вопрос в отчёт и перейти к следующему блоку,
а не решать самому.

РЕЖИМ РАБОТЫ

Автора за клавиатурой нет. Закончил блок — коммить и иди к следующему, не
спрашивая. Останавливайся только на том, что план прямо помечает как
требующее решения автора. Дошёл до конца плана — напиши итог и остановись:
дальше по своей инициативе ничего не добавляй.
```

## Промпт А — аудит без правок

```
Проект «Учебный навигатор» — Telegram-бот для подготовки КСП/КТП и конспектов
уроков. По PLAN.md работал другой исполнитель. Твоя задача — приёмка.

КОД НЕ ПРАВИТЬ. НИ ОДНОЙ СТРОКИ. Только читать, запускать и проверять.

Прочитай MASTER.md, PLAN.md, NIGHT_REPORT.md, затем git log за период работы
и git diff по каждому коммиту. Папку archive/ не открывать.

Проверь по пунктам и напиши отчёт:

1. СООТВЕТСТВИЕ ПЛАНУ. По каждому блоку: сделано / сделано частично / не
   сделано. Где отчёт говорит «закрыт», а по коду видно что нет, — писать прямо.

2. ГРАНИЦЫ. Двумя отдельными проверками, до всего остального:
   - нет ли в коде аналитики покрытия программы (эмбеддинги, косинусная
     близость, отчёты о покрытии). Ничего этого быть не должно — этот этап
     отложен автором;
   - нет ли ветки «конспект без аудиозаписи». Конспект делается только из
     настоящей записи.
   Нашёл — это первым пунктом отчёта, выше всех остальных находок.

3. ЛОВУШКИ ИЗ ПЛАНА. В разделе 2 плана и в каждом блоке выписаны ловушки.
   Проверь каждую отдельно, они там не для красоты. Особое внимание:
   - режим «для учителя» не должен вызывать LLM вообще (блок К0) — проверять
     по логу, а не по коду;
   - раздел опорных реплик не должен превратиться в пересказ всего урока (К1);
   - build_prompt не форкнут в две функции (К2);
   - порядок регистрации хендлеров: кнопки меню и «Назад» выше хендлеров
     состояний;
   - ffmpeg/whisper/soffice вызываются через asyncio.to_thread;
   - аудиофайлы удаляются и при провале расшифровки тоже;
   - пароль администратора не попал в репозиторий (блок Л1).

4. ЧЕСТНОСТЬ ТЕСТОВ. Прогони pytest сам. Отдельно посмотри: нет ли тестов,
   которые проверяют факт вызова функции вместо результата; нет ли try/except,
   проглатывающих ошибку ради зелёного прогона; не ходят ли тесты в реальную
   storage/app.db. Последнее проверяется так: снять дамп базы до и после
   прогона и сравнить, исключив таблицу worker_heartbeat (её пишет живой бот,
   и она меняется сама по себе).

5. ГИГИЕНА КОММИТОВ. Ни следа ассистента в сообщениях. Не утянуты .env, база,
   бэкапы, модели whisper, папка archive/. Один блок — один коммит.

6. РЕАЛЬНАЯ ПРОВЕРКА, а не чтение кода. Собери настоящий документ, прогони
   настоящую генерацию, посмотри на результат. ВАЖНО: запускать в том же
   окружении, что и бот. У launchd PATH только системный, а ffmpeg и whisper
   лежат в /opt/homebrew/bin — если проверять из своего шелла, ошибки этого
   класса не воспроизведутся. Если для проверки нужен запущенный бот или
   ключ, которого нет, — так и напиши, не выдавай чтение кода за проверку.

7. ЧТО СЛОМАЛОСЬ ИЗ СТАРОГО. Проверь, что работавшее раньше работает:
   /generate до конца, docx приходит, форма приказа №130 не поехала, порядок
   колонок «Ход урока» прежний.

Отчёт — файл AUDIT.md. Структура: найденное по убыванию тяжести, у каждого
пункта файл и строка, чем это грозит на живом использовании, и предлагаемое
исправление. Отдельно — список того, что проверить может только автор руками.

Ничего не чинить. Отчёт и стоп.
```

## Промпт И — исправление найденного

```
Есть отчёт AUDIT.md, автор его прочитал. Чини то, что в нём отмечено к
исправлению.

Правила те же, что при работе по плану: git add/commit можно, push/pull/
merge/rebase/reset --hard/tag/init и gh — нельзя. Ноль следов ассистента в
коммитах. Формат сообщения: «stage-ux: краткое описание правки». Всё
по-русски. Новых зависимостей нет.

Порядок:
  - по одному пункту отчёта за раз, от тяжёлого к лёгкому;
  - каждая правка — отдельный коммит с явным перечислением файлов;
  - после каждой правки — pytest целиком, не только новый тест;
  - на каждый исправленный баг — тест, который падал бы ДО правки. Проверить
    это временным откатом правки, а не поверить на слово. В отчёте написать,
    сколько тестов упало на откате;
  - если правка меняет поведение бота — перезапустить его и проверить в
    Telegram.

Чего НЕ делать:
  - не рефакторить соседний код «заодно» — только то, что в отчёте;
  - не переписывать блоки, которые в отчёте признаны рабочими;
  - не глушить проблему try/except, если не понял причину. Не понял — напиши
    в отчёт, что не понял, это честнее.

Закончив, допиши в AUDIT.md раздел «Исправлено»: по строке на пункт с номером
коммита. Что осталось неисправленным и почему — тоже списком, без умолчаний.
```

## Чем Codex и Gemini отличаются от предыдущего исполнителя

Практические заметки, не часть промптов.

- **Оба хуже держат длинный контекст.** Поэтому `PLAN.md` сделан
  самодостаточным, а архив убран из репозитория: чем меньше файлов в корне,
  тем меньше шансов, что исполнитель начнёт работать по устаревшему плану.
- **Оба склонны «улучшать заодно».** В промпте это запрещено дважды —
  в разделе «что делать» и в списке «чего не делать». При приёмке смотреть
  `git diff` на предмет правок, которых блок не просил.
- **Оба склонны объявлять сделанным непроверенное.** Отсюда требование
  проверять падение теста временным откатом, а не рассуждением, и называть
  в отчёте конкретное число упавших тестов.
- **Проверять окружение.** Самая дорогая ошибка этого проекта — проверка из
  своего шелла вместо окружения бота: у launchd другой `PATH`, и транскрипция
  с PDF там не работали, хотя «всё проходило». Это вынесено в промпт аудита
  отдельным абзацем.
